### Подготовка и граница

Встроенная граница ядра: одноразовый **AppContainer + Job Object + NTFS DACL**.
Нет виртуализации, сторонних драйверов, ProcessDeviceMap или изменения DACL
корня NPFS. LOCAL DLL вне workspace перенаправляет только `\\?\pipe\uv\` /
`\\.\pipe\uv\` в `\\.\pipe\LOCAL\uv\`; реальные каналы CROT/Docker не меняются.
Прослойка применяется к Node-потомкам. Job завершает всё дерево.

Владелец явно подготавливает NUL (первая команда — в административной
PowerShell), затем поставляет компоненты от учётной записи сервиса.
Управление loopback только своего SID выполняется при аренде; недостаточные
права или отсутствие подготовки выявляет self_test, без автоповышения прав:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/l1-install-win.ps1 -Apply
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/l1-components-win.ps1 -StateDirectory C:\path\to\crot-state
```

Сборка DLL требует Windows SDK/C++; скрипты не повышают права автоматически
и не скачивают код. Manifest `windows-l1-v1` фиксирует SHA-256 DLL и копии Node;
проверяются состав, версия, архитектура, single-link/reparse и owner-only DACL.
Компоненты имеют Medium/NW; WAL, секреты, профили и admission — Medium/NWNR.
Только ограниченный одноразовый изменяемый runtime получает Low/NW и
owner-only DACL до добавления SID аренды. Пользовательский workspace не
перемаркируется. Перенаправленный Windows `Packages/<profile>/AC/Temp`
создаётся внутри приватного runtime, не в настоящем домашнем каталоге.
Копия Docker CLI для актора не используется доверенным хостовым upstream.

### Сеть, Docker и статус

- `network=off`: ноль сетевых capabilities, без loopback-исключения.
- `network=on`: три стандартные capabilities и loopback только для своего SID;
  интернет/LAN/localhost доступны. CROT HTTP требует секретный http-token;
  настоящий CROT-6A по-прежнему получает EPERM, HTTP без токена — 401.
- Docker: нативный LOCAL endpoint в пакетном пространстве сессии, явный DACL
  только владельцу и SID аренды; фиксированный DOCKER_HOST. Прямой docker_engine,
  контексты/ключи хоста не передаются актору. Общая политика a–d запрещает
  защищённые mounts, запись вне workspace/приватного runtime, privileged,
  опасные capabilities/namespaces; отказ HTTP 403 и confinement.docker_refused.
- Проверяются Windows drive-aware пути и удержанные native identity. UNC,
  reparse, device/WSL-алиасы и неквалифицированные преобразования путей daemon
  не объявляются поддержанными. Нативная квалификация транспорта использует
  контролируемый upstream, **не реальный Docker daemon / всю матрицу Desktop/WSL**.
- AD-20.14 сохранён: неаутентифицированные host/network endpoints выполнения
  (включая Docker TCP без TLS) при network=on — остаточный риск владельца,
  сообщаемый в detail, не скрытое урезание сети и не причина отказа.
- Только реальный стартовый self_test разрешает available=true, reason=null,
  mechanism=windows-appcontainer в crot_status/overview. Причины отказа:
  components_missing, components_mismatch, private_storage_unavailable,
  self_test_failed. Remote без готовности получает CONFINEMENT_UNAVAILABLE;
  сбой после допуска — CONFINEMENT_FAILED без неизолированного повтора.
  Локальный full_control остаётся неограниченным по AD-13/AD-23.

### Восстановление и ограничения параллелизма

До ACL mutation: fsync/WAL, долговечные intent/receipt свежего профиля и no-share
lock. При старте/остановке CrotService/Core: остановка Job/реального SID токена,
полный preflight чужих ACE, восстановление исходных дескрипторов по NTFS ID,
снятие только своего SID с новых workspace-узлов, очистка своего loopback и
удаление профиля последним. Переименование не подменяется возвратом к старому
имени. Многоссылочные файлы (включая внешние hardlink) консервативно read-only;
восстановление не зависит от того, какое имя hardlink вернул OpenFileById.

Удалённый исходный обычный файл: ERROR_FILE_NOT_FOUND либо квалифицированный
NTFS stale-ID результат 87 **только** с сохранённой single-link identity и
успешным независимым by-ID контролем живого workspace на том же томе.
Один ERROR_INVALID_PARAMETER не считается отсутствием. Защищённые/runtime/link
объекты не получают этого исключения. Неоднозначность — fail closed.

Общие предки не допускают наложения независимых ACL-транзакций: одна машинная
аренда `%ProgramData%\CROT-Windows-L1-Admission`, owner-only/NR, no-share lock и
fsync/SHA-256 журнал владельца. Другой stateDir не усыновляет незакрытую аренду;
сначала исходный сервис восстанавливает свой WAL. Native CI-файлы сериализованы.
Повреждённые/открытые WAL и неоднозначные intent-only профили сохраняются,
а не выдаются за успех. Закрытые доказательства ограниченно ротируются.

## Linux (WP-23a)

Implements [ARCHITECTURE.md §27 AD-20](../ARCHITECTURE.md). In workspace
(`sandbox`) mode every child of `shell_run`, `process_exec` and
`process_start` runs inside one sandbox per Core: a CROT-owned bubblewrap
(`crot-bwrap`) under the CROT AppArmor policy, with `crot-l1-init` as PID 1.
In `full_control` L1 does not apply to local principals. Remote principals
(WP-31, ARCHITECTURE.md §27 AD-23 point 7) always need L1 for these
operations, in every local mode: in the remote default profile their
commands run in L1; under the user's remote full-control opt-in for their
device they run unconfined, but only where L1 is available, and each shell
command needs the user's approval.

Supported: Ubuntu 22.04 LTS and 24.04 LTS, x86_64 and arm64 (GA and HWE
kernels). Other systems report L1 as not available with a reason code.

## Linux: What a confined command sees

| Area | Inside L1 |
| --- | --- |
| Host file system | read-only, except the paths below |
| CROT-protected paths (state, logs, secret files, control credential, …) | replaced by empty, inaccessible entries |
| Keyrings, secret-store and browser-profile data of point 6, `$XDG_RUNTIME_DIR` | hidden; a private runtime directory with only `SSH_AUTH_SOCK` and the GnuPG agent sockets bound back |
| Workspace | read-write (the real files) |
| `/tmp`, `/var/tmp` | private per sandbox, removed with it |
| Home | private overlay layer: reads see the real home, writes stay in a CROT-private layer (tool caches persist between commands of the Core); see "Home directories of another group" below |
| Network | `confinement.network: "on"` (default): the host network, `localhost` works; `"off"`: a loopback-only network shared by the Core's confined processes |
| Abstract Unix sockets | host sockets (session bus, X11, …) denied by AppArmor; sockets between confined processes work |
| User namespaces | nested ones are refused (24.04: AppArmor `userns`; 22.04: `--disable-userns`) |
| Processes | own PID namespace, no-new-privileges, the whole tree is ended when the command (or the Core) ends |
| Docker | `DOCKER_HOST` points at the CROT Docker endpoint (below); the daemon's socket, contexts' TLS material and `DOCKER_CERT_PATH` are hidden |

### Home directories of another group

The sandbox's user namespace maps only the user's uid and primary gid
(unprivileged bubblewrap), and overlayfs refuses to copy up an entry whose
owner or group has no mapping there (`EOVERFLOW`, "Value too large for
defined data type"). A directory the user owns with a supplementary group —
`~/.docker` of group `docker` on the GitHub runners — could therefore not
receive new entries (`docker buildx`: `mkdir ~/.docker/buildx`). When a
sandbox starts, the service lists such directories in the home and in each
file system mounted below it (breadth first, at most 20 000 directories;
other owners' directories, symbolic links, the workspace and hidden entries
are not entered) and mounts a *group layer* of empty copies owned by the
user's uid and gid, with the host's modes and times, as a lower layer
directly above the real directory. The contents still come from the real
home, writes still go only to the private layer, and the user's permissions
are unchanged (they are decided by the owner bits, which are the same).
Remaining limitation: an existing *file* of another group cannot be modified
in place (`EOVERFLOW`); replacing it (write a new file, rename) works.

Configuration (owner only, part of the configuration digest):

```json
{ "confinement": { "network": "on" } }
```

## Linux: Status and errors

`crot_status` (and the tray / control overview) report `confinement`:
`mechanism`, `available`, `network`, `reason`, `detail`. Reason codes:
`not_implemented`, `userns_unavailable`, `components_missing`,
`components_mismatch`, `apparmor_unavailable`,
`apparmor_profile_not_loaded`, `apparmor_unix_mediation_unavailable`,
`overlay_unavailable`, `private_storage_unavailable`, `self_test_failed`.
Availability is decided by a self-test of the real sandbox (canary in a
protected path, write boundary, label, nested user namespace). In
`full_control` the `detail` starts with "permission mode full_control: local
commands run unconfined; remote commands need L1". `crot_status` `remote`
(WP-31) lists the L1 requirement among the restrictions of the remote
profile.

- **`CONFINEMENT_UNAVAILABLE`** — L1 is not available when a **remote**
  principal asks for a command: refused before admission, nothing started,
  audited. This holds in every local mode and under the remote full-control
  opt-in (AD-23 point 7). macOS follows AD-31 below; Windows
  follows AD-30 above. Local principals without initial L1 admission keep the previous
  (unconfined) behaviour and see the reason in `crot_status`.
- **`CONFINEMENT_FAILED`** — L1 was available, but the sandbox could not
  start this command. The command is never retried outside L1; the status is
  refreshed.

## Linux: Docker endpoint (AD-20 point 9)

Each Core's sandbox gets a Unix socket served by the service. Requests are
forwarded to the daemon exactly as the service's Docker CLI would reach it
(Unix socket directly; TCP, TLS, SSH and contexts through
`docker system dial-stdio` with the service's Docker environment), including
upgraded/hijacked connections (attach, exec, BuildKit). The fixed checks:

- a. bind mounts and volume `device` options only inside the workspace, the
  private temp or the home layer (read-only sources elsewhere in the read
  view are allowed), never a CROT-protected or hidden path;
- b. no privileged containers or execs, no added capabilities, devices,
  host PID/IPC/UTS/user namespaces, `seccomp`/`apparmor`/`systempaths`
  `unconfined`, no `security.insecure` BuildKit entitlement;
- c. `--volumes-from` only from containers that pass the same checks;
- d. services (Swarm) checked like containers.

A refusal is HTTP 403 with `CROT L1 Docker endpoint refused the request: …`
and an audit record `confinement.docker_refused` (request kind and reason,
never a payload). For a daemon on this host that supports AppArmor, new
containers get the profile `crot-l1-container-<v>`. `docker.use` (AD-3) is
unchanged; the endpoint adds no permission or approval rules.

## Linux: Installing the components (until WP-34)

The service never installs or loads anything and has no setuid part. For
source checkouts and CI:

```sh
sudo apt-get install -y gcc meson ninja-build pkg-config libcap-dev xz-utils curl apparmor python3
sudo bash scripts/l1-install.sh install   # build and install /usr/lib/crot/l1/<v>, load the policy
bash scripts/l1-install.sh status
sudo bash scripts/l1-install.sh remove
```

`install` downloads bubblewrap 0.11.0
(`988fd6b232dafa04b8b8198723efeaccdb3c6aa9c1c7936219d5791a8b7a8646`,
checked; `CROT_L1_BWRAP_TARBALL` uses a local copy), builds `crot-bwrap` and
`crot-l1-init`, installs them root-owned with `manifest.json`, renders the
policy for the release's AppArmor ABI (4.0 on 24.04, 3.0 on 22.04;
`CROT_L1_ABI` overrides) into `/etc/apparmor.d/crot-l1-<v>` and loads it.

Host application profiles: a stacked exec also attaches loaded host profiles
whose attachment matches the executed path (Ubuntu 24.04 ships
`flags=(unconfined)` profiles with `userns,` for Google Chrome, Edge,
Brave, Chromium builds and others). `install` therefore adds to
`crot-l1-<v>` one exact rule `allow ix "<path>",` for each literal
attachment of a host profile in `/etc/apparmor.d` that is loaded as
`unconfined`, has `flags=(unconfined)` and grants `userns,`
(`scripts/l1-host-exec.py`; `CROT_L1_APPARMOR_DIR`,
`CROT_L1_APPARMOR_PROFILES`, `CROT_L1_MULTIARCH` override its inputs). Such
a program keeps the L1 label inside the sandbox (no user namespace, the
payload's peer rules) instead of running as `chrome//&crot-l1-<v>//&…`,
whose own IPC the L1 peer rules deny (AD-20 point 3, amendment). Run
`install` again after installing a browser or another application that
brings such a profile; enforcing host profiles are left in the stack.
The version `<v>` and the bubblewrap release are read from
`src/native-host/linux-l1/components.ts`; the service only accepts
components of its own `<v>` with matching digests.

bubblewrap options relied on: `--unshare-user --unshare-pid --unshare-ipc
--unshare-uts --unshare-cgroup-try --unshare-net --disable-userns
--die-with-parent --new-session --clearenv --setenv --ro-bind --bind
--bind-try --dev --dev-bind-try --proc --tmpfs --perms --overlay-src
--overlay --chdir`.

## Linux: Known limits

- Host-local services reachable over the host network (Docker on TCP without
  TLS, an SSH server accepting the user's keys, …) are a residual risk
  (AD-20 point 14); an SSH daemon is treated as not local, so its containers
  get no CROT profile.
- The BuildKit `security.insecure` check scans the gRPC stream; an
  entitlement split across HTTP/2 frames may be missed by the endpoint (the
  daemon still requires its own configuration to grant it).
- Containers created before L1 and started from inside are not re-checked.
- A workspace that contains a CROT-protected path is bound with that path
  hidden.
- Host application profiles installed after `install`, and host profiles
  with globbed attachments, get no exact rule until `install` runs again;
  such a program then runs in the stack with its host profile, and its IPC
  may be denied (fail closed, the boundary is unchanged).

## macOS L1 — Seatbelt, WP-23b / AD-31

Производственный `macos-seatbelt` регистрируется NativeHost, без kext/VM и
без изменения глобальных прав. Требуются Apple `/usr/bin/sandbox-exec`,
`libproc`, `libsandbox`, пакетный Koffi и приватный owner-only temp. Root не
объявляется поддержанной учётной записью сервиса. Стандартный пользователь не
получает автоматического повышения прав. Компоненты отсутствуют/не подходят:
`components_missing` / `components_mismatch`; нет приватного temp —
`private_storage_unavailable`; нативные инварианты не доказаны — `self_test_failed`.

До `available=true, reason=null` обязательны реальные canary/control IPC,
workspace/temp writes, kernel policy identity и невозможность повторного
применения как исходного, так и заранее скомпилированного профиля.
Remote до допуска получает `CONFINEMENT_UNAVAILABLE`; post-admission failure
даёт `CONFINEMENT_FAILED`, без обходного запуска вне Seatbelt. Local
full_control не меняется; старый local fallback допустим только до первого
допуска. Статусы `crot_status` и overview используют один CoreConfinement.

- Пути `/var`/`/tmp`, отсутствующие листья и симлинки канонизуются. SBPL
  фиксирован, кавычки экранируются; пользовательский профиль не принимается.
- Чтение хоста разрешено, кроме CROT state/config/audit/secrets, Keychain,
  Docker contexts/credentials и прямых Unix endpoints. securityd/управляющий
  Mach IPC не разрешён. HTTP без недоступного песочнице токена получает 401.
- Запись — canonical workspace, private HOME/cache/temp и минимальные
  `/dev` устройства. Node/CROT runtime/зависимости read-only. Существующие
  внешние hardlink требуют read-only aliases; внутренние известные hardlink
  writable. Protected file с nlink>1 отвергается, а не объявляется безопасным.
- Preflight до каждого запуска: не следовать workspace-симлинкам, учитывать
  inode по dev/ino, раскрывать protected-симлинки; неизвестные/новые цели,
  недоступный обход и предел 100000 узлов на проход — fail closed. Это
  консервативное ограничение производительности/доступности, не тихий пропуск.
- HOME/cache эфемерны на Core; нет APFS overlay и переноса секретных
  пользовательских конфигураций. npm/pip/Cargo/Go пишут в private caches.
  Установленные Rust toolchains доступны только для чтения через приватные
  ссылки и минимальную приватную selection metadata; credentials не копируются.
  Инструменты должны быть установлены и присутствовать в настроенном PATH.
- network=on: IP internet/LAN/host localhost; off: только host loopback и свой
  Docker Unix endpoint. Это общий стек хоста, не отдельный namespace.
- Unix Docker proxy с private parent directory и fixed DOCKER_HOST использует
  общий AD-20.9 a–d фильтр: 403 и `confinement.docker_refused`. Native byte
  stream проверен с mock upstream; реальный daemon/Compose/TLS/SSH matrix
  этим не квалифицирован. AD-20.14 (неаутентифицированные host/TCP endpoints
  выполнения при network=on) остаётся риском владельца, без скрытого урезания сети.
- Остановка — per-command kernel identity, не PPID/группа. Прямой setsid/setpgid
  запрет не покрывает posix_spawn SETSID; этот отрицательный результат сохранён.
  Trusted ACK допускает caller code только после проверки identity. Guardian
  вне песочницы на EOF приватного не наследуемого pipe завершает также
  detached/reparented actors после SIGKILL владельца и удаляет private temp.
  Сбой guardian закрывает admission и завершает принадлежащих акторов.

### macOS: пределы доказательств

[Нативная квалификация, восемь критериев и точные CI/SHA](design/macos-l1-production.md).
Цель: Apple-shipped macOS15/26/27 и x64/arm64, Node20/22 (Intel не
заявляется для macOS27). Фактический CI: macOS26.6.2 arm64 Node20/22.
Остальные сочетания — цель, не выдуманные тесты. Предикаты + self_test решают
готовность конкретного хоста; unsupported OS/arch и root дают mismatch.

Seatbelt и часть native API deprecated/private: обновление ОС может сделать
механизм недоступным. PID/UID/birth/profile перепроверяются перед сигналом,
но атомарного pidfd нет; администраторы и несвязанные host-процессы того же
пользователя не изолированы и могут менять/останавливать сервис. Квалификация
не заменяет независимое security review, подписанную поставку и полный v1 gate.

macOS loopback при network=off также принадлежит хосту: неаутентифицированный
localhost endpoint выполнения может стать обходным исполнителем вне Seatbelt.
Это остаточный риск модели доступного localhost, а не доступ к CROT без токена;
status.detail предупреждает об общей host IP/loopback authority.
