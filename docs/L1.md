# Command confinement L1 on Linux (WP-23a)

Implements [ARCHITECTURE.md §27 AD-20](../ARCHITECTURE.md). In workspace
(`sandbox`) mode every child of `shell_run`, `process_exec` and
`process_start` runs inside one sandbox per Core: a CROT-owned bubblewrap
(`crot-bwrap`) under the CROT AppArmor policy, with `crot-l1-init` as PID 1.
In `full_control` L1 does not apply to local principals. Remote principals
(WP-31, ARCHITECTURE.md §27 AD-23 point 7) always need L1 for these
operations, in every local mode: in the remote default profile their
commands run in L1; under the user's remote full-control opt-in for their
device they run unconfined, but only where L1 is available, and each shell
command needs the user's approval.

Supported: Ubuntu 22.04 LTS and 24.04 LTS, x86_64 and arm64 (GA and HWE
kernels). Other systems report L1 as not available with a reason code.

## What a confined command sees

| Area | Inside L1 |
| --- | --- |
| Host file system | read-only, except the paths below |
| CROT-protected paths (state, logs, secret files, control credential, …) | replaced by empty, inaccessible entries |
| Keyrings, secret-store and browser-profile data of point 6, `$XDG_RUNTIME_DIR` | hidden; a private runtime directory with only `SSH_AUTH_SOCK` and the GnuPG agent sockets bound back |
| Workspace | read-write (the real files) |
| `/tmp`, `/var/tmp` | private per sandbox, removed with it |
| Home | private overlay layer: reads see the real home, writes stay in a CROT-private layer (tool caches persist between commands of the Core); see "Home directories of another group" below |
| Network | `confinement.network: "on"` (default): the host network, `localhost` works; `"off"`: a loopback-only network shared by the Core's confined processes |
| Abstract Unix sockets | host sockets (session bus, X11, …) denied by AppArmor; sockets between confined processes work |
| User namespaces | nested ones are refused (24.04: AppArmor `userns`; 22.04: `--disable-userns`) |
| Processes | own PID namespace, no-new-privileges, the whole tree is ended when the command (or the Core) ends |
| Docker | `DOCKER_HOST` points at the CROT Docker endpoint (below); the daemon's socket, contexts' TLS material and `DOCKER_CERT_PATH` are hidden |

### Home directories of another group

The sandbox's user namespace maps only the user's uid and primary gid
(unprivileged bubblewrap), and overlayfs refuses to copy up an entry whose
owner or group has no mapping there (`EOVERFLOW`, "Value too large for
defined data type"). A directory the user owns with a supplementary group —
`~/.docker` of group `docker` on the GitHub runners — could therefore not
receive new entries (`docker buildx`: `mkdir ~/.docker/buildx`). When a
sandbox starts, the service lists such directories in the home and in each
file system mounted below it (breadth first, at most 20 000 directories;
other owners' directories, symbolic links, the workspace and hidden entries
are not entered) and mounts a *group layer* of empty copies owned by the
user's uid and gid, with the host's modes and times, as a lower layer
directly above the real directory. The contents still come from the real
home, writes still go only to the private layer, and the user's permissions
are unchanged (they are decided by the owner bits, which are the same).
Remaining limitation: an existing *file* of another group cannot be modified
in place (`EOVERFLOW`); replacing it (write a new file, rename) works.

Configuration (owner only, part of the configuration digest):

```json
{ "confinement": { "network": "on" } }
```

## Status and errors

`crot_status` (and the tray / control overview) report `confinement`:
`mechanism`, `available`, `network`, `reason`, `detail`. Reason codes:
`not_implemented`, `userns_unavailable`, `components_missing`,
`components_mismatch`, `apparmor_unavailable`,
`apparmor_profile_not_loaded`, `apparmor_unix_mediation_unavailable`,
`overlay_unavailable`, `private_storage_unavailable`, `self_test_failed`.
Availability is decided by a self-test of the real sandbox (canary in a
protected path, write boundary, label, nested user namespace). In
`full_control` the `detail` starts with "permission mode full_control: local
commands run unconfined; remote commands need L1". `crot_status` `remote`
(WP-31) lists the L1 requirement among the restrictions of the remote
profile.

- **`CONFINEMENT_UNAVAILABLE`** — L1 is not available when a **remote**
  principal asks for a command: refused before admission, nothing started,
  audited. This holds in every local mode and under the remote full-control
  opt-in (AD-23 point 7). On macOS and Windows L1 reports `not_implemented`
  until WP-23b/c, so remote shell and process operations are always refused
  there, with this explanation. Local principals keep the previous
  (unconfined) behaviour and see the reason in `crot_status`.
- **`CONFINEMENT_FAILED`** — L1 was available, but the sandbox could not
  start this command. The command is never retried outside L1; the status is
  refreshed.

## Docker endpoint (AD-20 point 9)

Each Core's sandbox gets a Unix socket served by the service. Requests are
forwarded to the daemon exactly as the service's Docker CLI would reach it
(Unix socket directly; TCP, TLS, SSH and contexts through
`docker system dial-stdio` with the service's Docker environment), including
upgraded/hijacked connections (attach, exec, BuildKit). The fixed checks:

- a. bind mounts and volume `device` options only inside the workspace, the
  private temp or the home layer (read-only sources elsewhere in the read
  view are allowed), never a CROT-protected or hidden path;
- b. no privileged containers or execs, no added capabilities, devices,
  host PID/IPC/UTS/user namespaces, `seccomp`/`apparmor`/`systempaths`
  `unconfined`, no `security.insecure` BuildKit entitlement;
- c. `--volumes-from` only from containers that pass the same checks;
- d. services (Swarm) checked like containers.

A refusal is HTTP 403 with `CROT L1 Docker endpoint refused the request: …`
and an audit record `confinement.docker_refused` (request kind and reason,
never a payload). For a daemon on this host that supports AppArmor, new
containers get the profile `crot-l1-container-<v>`. `docker.use` (AD-3) is
unchanged; the endpoint adds no permission or approval rules.

## Installing the components (until WP-34)

The service never installs or loads anything and has no setuid part. For
source checkouts and CI:

```sh
sudo apt-get install -y gcc meson ninja-build pkg-config libcap-dev xz-utils curl apparmor python3
sudo bash scripts/l1-install.sh install   # build and install /usr/lib/crot/l1/<v>, load the policy
bash scripts/l1-install.sh status
sudo bash scripts/l1-install.sh remove
```

`install` downloads bubblewrap 0.11.0
(`988fd6b232dafa04b8b8198723efeaccdb3c6aa9c1c7936219d5791a8b7a8646`,
checked; `CROT_L1_BWRAP_TARBALL` uses a local copy), builds `crot-bwrap` and
`crot-l1-init`, installs them root-owned with `manifest.json`, renders the
policy for the release's AppArmor ABI (4.0 on 24.04, 3.0 on 22.04;
`CROT_L1_ABI` overrides) into `/etc/apparmor.d/crot-l1-<v>` and loads it.

Host application profiles: a stacked exec also attaches loaded host profiles
whose attachment matches the executed path (Ubuntu 24.04 ships
`flags=(unconfined)` profiles with `userns,` for Google Chrome, Edge,
Brave, Chromium builds and others). `install` therefore adds to
`crot-l1-<v>` one exact rule `allow ix "<path>",` for each literal
attachment of a host profile in `/etc/apparmor.d` that is loaded as
`unconfined`, has `flags=(unconfined)` and grants `userns,`
(`scripts/l1-host-exec.py`; `CROT_L1_APPARMOR_DIR`,
`CROT_L1_APPARMOR_PROFILES`, `CROT_L1_MULTIARCH` override its inputs). Such
a program keeps the L1 label inside the sandbox (no user namespace, the
payload's peer rules) instead of running as `chrome//&crot-l1-<v>//&…`,
whose own IPC the L1 peer rules deny (AD-20 point 3, amendment). Run
`install` again after installing a browser or another application that
brings such a profile; enforcing host profiles are left in the stack.
The version `<v>` and the bubblewrap release are read from
`src/native-host/linux-l1/components.ts`; the service only accepts
components of its own `<v>` with matching digests.

bubblewrap options relied on: `--unshare-user --unshare-pid --unshare-ipc
--unshare-uts --unshare-cgroup-try --unshare-net --disable-userns
--die-with-parent --new-session --clearenv --setenv --ro-bind --bind
--bind-try --dev --dev-bind-try --proc --tmpfs --perms --overlay-src
--overlay --chdir`.

## Known limits

- Host-local services reachable over the host network (Docker on TCP without
  TLS, an SSH server accepting the user's keys, …) are a residual risk
  (AD-20 point 14); an SSH daemon is treated as not local, so its containers
  get no CROT profile.
- The BuildKit `security.insecure` check scans the gRPC stream; an
  entitlement split across HTTP/2 frames may be missed by the endpoint (the
  daemon still requires its own configuration to grant it).
- Containers created before L1 and started from inside are not re-checked.
- A workspace that contains a CROT-protected path is bound with that path
  hidden.
- Host application profiles installed after `install`, and host profiles
  with globbed attachments, get no exact rule until `install` runs again;
  such a program then runs in the stack with its host profile, and its IPC
  may be denied (fail closed, the boundary is unchanged).

### Windows: продолжение проверки NPFS после 3f094a1

Привилегированный ProcessDeviceMap исключён из AppContainer launcher.
Квалификационный тест потомков сначала выдаёт свежему package SID на корне
NPFS только FILE_CREATE_PIPE_INSTANCE | FILE_READ_ATTRIBUTES | SYNCHRONIZE
(0x100084), без наследования. FILE_READ_DATA и FILE_WRITE_DATA не выдаются;
DACL существующих каналов не меняются. После полного drain Job исходный DACL
восстанавливается с побайтовой проверкой. Несовпадение с установленным состоянием
из-за конкурентного изменения — ошибка, не разрешение затереть чужую правку.
Это не production backend: аварийное восстановление, квалификация каналов,
сети и Docker остаются открытыми. Windows L1 остаётся unavailable.
