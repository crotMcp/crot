# WP-23c: встроенный Windows L1 после a6eb17d

**WP-23c не принят. PR #27 остаётся черновиком, производственный Windows
CommandConfinement недоступен. Linux, macOS и Windows обязательны для v1.**

Проверенный исходный коммит: `427116262a5c0045e1ab5d05b21bda4500274f94`.
Локально: **1737 Core + 147 extension**, 168 платформенных пропусков.
Настоящий CI: **9 не-Windows успешны, оба Windows неуспешны**.
Проверялся merge-коммит PR; второй родитель независимо сверён с исходным коммитом.

## Сделано после a6eb17d

- `c5016ed` — до кода записан AD-29: AppContainer без сетевых capabilities + Job,
  явная административная подготовка только NUL, управляемые ACE трёх деревьев,
  owner-only и запрещающие ACE защищённых ресурсов. Зафиксирована платформенная
  часть OD-9, разблокирована зависимость WP-23b. Это выбор направления, не приёмка.
  Windows Server 2022/2025 заявлен только на реально поставляемой x64;
  ARM64 обязателен для Windows 11, а не выдуман для Server.
- `fd4fd47` — отдельное исправление гонки POSIX/macOS: один endpoint-lock охватывает
  первичный bind, stale-recovery и chmod 0600. Новый тест падает на a6eb17d и
  проходит с исправлением. Причина всех прежних прерывистых сбоев не объявлена
  доказанной; актуальные macOS Node 20/22 проверяются настоящим CI.
- `66ab0f9` — активная нативная фикстура заменена на Windows SDK/AppContainer:
  нет загрузки MSI, виртуального диска, Dokan/WinFsp и стороннего драйвера.
  Проверяются фактические SID, capabilities, Low IL и Job до ResumeThread.
  Старые PowerShell/RPC gates и отказ производственного backend сохранены.
- `6a0b961`, `bddc97a` — исправлены кодировка скрипта для WinPS 5.1 и отображение
  GR/GW в конкретные файловые права NUL. Сохраняется точная проверка DACL,
  владельца и группы; SACL/IL не меняется. Сам сервис не повышает права.
  Старый каталог состояния защищается до bootstrap/чтения секретов; ABI-тест
  проверяет точный запрещающий ACE перед разрешением владельцу.
- `c4f53bd`, `7596791` — устранена гонка учёта Job после сигнала завершения,
  добавлены только три собственных stdio-дескриптора через HANDLE_LIST,
  исправлено quoting cmd. Минимальный прежний контракт снимка ACL сохранён;
  подробности доступны отдельно и содержат только хеши/флаги, не SID.
- `e67cb0e` — явно удаляются собственные разрешающий И запрещающий ACE:
  REVOKE_ACCESS сам по себе не удаляет ACCESS_DENIED_ACE. Временная фикстура
  проверяет неизменность прочих ACE перед восстановлением их происхождения;
  это не производственный журнал прав и не квалификация параллельных правок.
  WinPS явно запрашивает выбранный рабочий каталог и загружает штатные
  Utility/Management из собственного PSHOME. Проверка выявила отказ Set-Location;
  это НЕ успешное исправление совместимости.
- `4271162` — путь временного workspace канонизируется доверенным родителем до
  запуска AppContainer, без выдачи прав на родительские каталоги. Гипотеза о
  единственной причине в коротком RUNNER~1 опровергнута: WinPS отказывает и на
  полном пути. Точный дескриптор защищённого файла после очистки восстановлен,
  workspace — ещё нет. Оба провала сохранены в обязательном тесте.

## Проверяемый контрпример границы записи

На `7596791`, в **обоих настоящих Windows заданиях**, AppContainer получил
дескриптор с GENERIC_WRITE по заранее созданному имени `outside/alias.txt`,
которое является hardlink на `workspace/link-source.txt`:
`outsideHardlinkOpened=true`, `nativeCode=0x4352017f`.
Записи через этот дескриптор и чтения секретных байтов не выполнялись.
На последнем `4271162` результат воспроизведён на обеих версиях Node:
`outsideHardlinkOpened=true`, `nativeCode=0x4352017f`.
Восстановление дескрипторов: защищённый файл — точное совпадение; workspace — нет.

Обычная запись в независимый `outside/target.txt` отклоняется ядром. Защищённый
файл после настоящего `createServicePrivateFiles(true).protectFile` также
отклоняет оба открытия — чтение и запись. Это **контрольный файл**, не полный
CROT-6A реального сервиса/каналов.

ACE относится к файловому объекту, общему для hardlink, а не к одному имени.
Поэтому «у внешнего родительского каталога нет ACE песочницы» не доказывает
запрет открытия уже существующего внешнего имени этого объекта. Обязательный
отрицательный тест не удалён, не пропущен и не превращён в положительный.
Ни разрешённый внешний доступ, ни отказ до запуска не объявляются изоляцией.

До устранения этого случая одного AppContainer + трёх наследуемых ACE
недостаточно для доказанной строгой границы по путям. Выбор OD-6 в AD-29 не
означает, что его текущая реализация уже удовлетворяет требованиям.

## Журналы и следующий шаг

Полные журналы, успешные и неуспешные прогоны, ответы CI, проверенные родители
тестировавшихся merge-коммитов и SHA-256:
[`../evidence/windows-l1-native-os/`](../evidence/windows-l1-native-os/README.md).
Старые 198 хешей исторического манифеста не изменены. Пропуски Windows на
локальном Linux не засчитываются как нативная квалификация.

Следующий блокирующий шаг — архитектурно закрыть внешний hardlink и затем
доказать безопасную аренду ACE/восстановление, не возвращая сторонний драйвер и
не снижая требований. Отказ от небезопасного workspace ДО выдачи ACE — возможная
развилка требований, а не уже выполненный отрицательный runtime-тест. Она требует
отдельного решения; молча подменять ею текущий критерий нельзя.

Документированный CreateBindLink проверен, но не принят как обход: его изменения
действуют system-wide и требуют администратора, а не создают изоляцию одного
процесса. Read-only перенаправление всего хоста не применяется.
