# WP-23c: внутренние переименования и выбранный запуск AppContainer

**WP-23c не принят.** Последний проверенный исходный коммит: `a36a701b3b4d1b222f619a685880a5c9ab619625`.
PR27 остаётся черновиком. AppContainer + Job выбран без виртуализации,
сторонних драйверов и лицензионных платежей. Производственная регистрация
CommandConfinement не объявляется до квалификации всего жизненного цикла.

## Дельта после a6eb17d

Сохранены прежние PowerShell/RPC/native-process/CROT-6A гейты и отдельное
исправление macOS `fd4fd47`; прежние доказательства не переписаны.

- `0f9a998`: FILE_SHARE_DELETE только для обычных существовавших внутренних
  узлов workspace, без внешних hardlink; независимый набор расширен с 10 до
  13 дескрипторов. Запись и переименование существовавшего файла проходят.
- `1f015ff`: только отвергнутый Low WRITE_RESTRICTED spike переведён в явный
  opt-in CROT_WINDOWS_REJECTED_TOKEN_RESEARCH=1 по разрешению куратора.
  Его проверки не переписаны; выбранные AppContainer/WinPS/RPC/native-process
  и настоящий сервисный CROT-6A остаются обязательными.
- `9d43771`/`394c1e8`: владение свежим одноразовым профилем, проверка фактических
  AppContainer/SID/нулевых capabilities/Low IL до ResumeThread, штатный байтовый
  NativeProcessLauncher и Job. Ошибочное LPWSTR-декодирование исправлено;
  отдельный скомпилированный тест проверяет UTF16/allocator ABI. Неуспешный
  Windows-прогон 9d43771 без пакета событий сохранён как неуспех, не как отказ доступа.
- `394c1e8` и последующие Windows-прогоны доказывают 1 МиБ бинарного stdin/stdout,
  256 КиБ stderr, Unicode argv и настоящий exit=23, а также EPERM на чтение,
  запись защищённого canary и запись вне workspace через выбранный запуск.
- `5d4791d`: исправлена фактическая защита от переименования. Метаданные сами
  по себе не обеспечивали запрет DELETE sharing; добавлен отдельный read/list
  guard без DELETE sharing. Все пять защищённых объектов отклоняют владельцу
  переименование с Win32=32. Корень, предки, защищённые файлы и внешние hardlink
  не получили FILE_SHARE_DELETE. Для полностью внутренних hardlink отдельный
  guard снимается только после проверки всех имён; их чтение/запись сохранены.
- `9dd1107`: изолированный контроль NTFS без изменения ACL показал: открытый
  дочерний файл блокирует переименование его каталога с Win32=5 даже при
  FILE_SHARE_DELETE; после закрытия того же handle операция успешна. Открытый
  handle самого каталога с DELETE sharing не блокирует эту операцию. Это не
  отказ DACL AppContainer: у владельца наблюдается тот же результат.

- `bd96740`: устранён реальный отказ переименования каталога. Только обычные
  существовавшие single-link файлы освобождают открытые handles на время акторов.
  После завершения всех Job они открываются через OpenFileById по исходному
  идентификатору NTFS, с проверкой тома, file index, типа и времени создания;
  дескриптор принимается только после проверки идентичности. Чужие ACE/control
  сверяются до восстановления; старое имя не используется как запасной путь.
  Корень, предки, защищённые файлы и внешние ссылки остаются удержанными.
  На обоих Node все семь операций записи/переименования успешны, три обычных
  файла повторно открыты по ID, исходные SD **13/13**, cleanup=true, CROT-6A сохранён.
- `a36a701`: конечный контроль создания только собственных свежих pipe instances,
  без повторов и без изменения общих ACL. Полные коды для обычного пространства,
  точного пространства libuv и LOCAL, с default/явным частным DACL, сохранены
  в nativeDiagnostics.pipeCreationDiagnostics. На Node20/22 обычный и точный
  libuv namespace возвращают Win32=5 даже при явном частном DACL; LOCAL
  успешно создаётся и закрывается с кодами 0. Гейт потомка остаётся неуспешным:
  трасса останавливается перед возвратом синхронного child_process.spawn().
  Подмена теста вариантом без захвата вывода, пропуск или обход защиты не добавлены.

## Восемь критериев приёмки

Ранее полностью зелёный базовый исходный коммит — `de18eca`.
Продолжение: `3d17e6d` (WAL/lock/recovery protocol), `51d9ae6` (native SD
transactions), `4c22e59` (24-byte FILE_ID_DESCRIPTOR, NTFS/ACE bounds).
Нативные проверки новых компонентов не являются приёмкой всего Windows L1.

| № | Критерий | Подтверждено / остаётся | Статус |
| --- | --- | --- | --- |
| 1 | Обычные API, существовавшие узлы, точный ACL | Повторно на `4c22e59`: 7/7 CRUD/rename, 13/13 SD, cleanup=true. Новый WAL сохраняет исходный и запланированный SD до изменения ACL | Гейт пройден; полное аварийное восстановление аренды не принято |
| 2 | Процессы, stdio, Job и потомки | На `4c22e59` LOCAL только для libuv; Node → Node → Node, оба потомка завершаются через Job; 1 МиБ stdin/stdout, 256 КиБ stderr, Unicode, exit=23 | Гейт пройден на Node20/22 Server2025 x64 |
| 3 | Граница записи и hardlink/reparse/гонки | 5/5 защищённых подмен отклонены, внешние hardlink без записи. Новый recovery component отказывает при многоссылочных файлах, чужом SD/повторном ID | Частично: полная матрица гонок/путей не принята |
| 4 | Настоящие секреты, состояние, аудит и IPC | Реальный CROT-6A: 5 чтений +5 записей +настоящий канал=EPERM, состояние неизменно. WAL отдельно проверяется на read/write EPERM | Сервисный гейт пройден; не подменяет остальные свойства L1 |
| 5 | Node20/22, cmd/WinPS, ОС/архитектуры/обычный пользователь | Проверен Server2025 x64; Node/cmd/WinPS/NUL и потомки. Windows11/Server2022/ARM64/обычный пользователь требуют своих запусков | Частично; матрица не принята |
| 6 | Регрессии и зелёный CI | `4c22e59`: Windows20/22 + 8 остальных PASS; browser-e2e FAIL на select_option. Повторный прогон нового HEAD обязателен | 10/11; ошибку браузера не объявляем исправленной изменениями Windows |

## CI и границы доказательств

`3d17e6d`: Windows подтверждает сохранение WAL после убийства владельца,
освобождение OS lock без удаления lock-файла и реальный AppContainer read/write
WAL=EPERM. В первом прогоне POSIX-тестовый provider ошибочно ставил 0600 на
каталог: исправлено на 0700 в `51d9ae6`, без ослабления защиты данных.

`51d9ae6`: первая нативная проверка открытия по сохранённому ID выявила
Win32=87. `FILE_ID_DESCRIPTOR` должен иметь размер 24 (из-за union FILE_ID_128),
не 16; исправлено в `4c22e59`. ABI/формат/границы ACE проверяются переносимыми
тестами. На `4c22e59`, merge `1ec46cc`, оба Windows задания PASS: шесть native
ACL transaction тестов, три WAL crash boundary и отдельное восстановление двух
точных SD после убийства владельца. Повторно: 13/13 исходных SD, 7/7 CRUD,
5/5 tamper, реальный CROT-6A 5+5+канал EPERM, Node → Node → Node/Job.
Общий CI этого коммита 10/11: browser-e2e падает на browser_select_option;
причина не приписывается Windows-коду и не считается устранённой.

Новый crash-тест SD намеренно узкий: два дескриптора NTFS, отсутствие акторов
и реального профиля указано в evidence. Это не доказательство orphan Job drain,
удаления профиля либо полноценного service startup/shutdown. Подставные callbacks
в протокольных тестах не выдаются за реализацию этих недостающих частей.

Фактические Windows-прогоны — Server2025 x64, Node20/22. Это не проверка
Windows11, Server2022, ARM64 или обычного пользователя. Все три ОС обязательны
для v1. Исторические независимые SD и декодированные события сохраняются в
`docs/evidence/windows-l1-internal-rename/`; новые bounded evidence публикуются
reporter-ом в аннотациях соответствующего CI run, без секретов/их содержимого.

## Следующий шаг

Подключить полноценный нативный адаптер: свежесть/квитанции владения профилем,
удержание корня/предков/защищённых объектов, доказательство смерти всех акторов,
снятие своих ACE с новых объектов workspace и удаление профиля после восстановления.
Проверить остановку сервиса в каждой точке между WAL/ACL/Job/Resume/cleanup.
Закрытые WAL пока сохраняются как tombstones: лимит 64 означает безопасный отказ;
производственная ротация ещё нужна. Общие ancestor leases параллельных Core
пока не разделяются: пересечение идентичностей отказывает до второй мутации.

Затем — production CommandConfinement, сеть on/off и localhost, защищённый
Docker endpoint/аудит, компоненты поставки и вся матрица. Текущий AD-29 требует
нулевые сетевые capabilities: полноценный network=on требует отдельного явно
зафиксированного решения, не молчаливого ослабления. До приёмки Windows remote
sandbox остаётся CONFINEMENT_UNAVAILABLE; обхода контрактов отказа нет.
