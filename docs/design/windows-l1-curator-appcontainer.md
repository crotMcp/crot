# WP-23c: точный ACL и реальный CROT-6A

**WP-23c не принят.** Последний проверенный исходный коммит:
`595ea7969e83c8078a44d6123d127b728f2fadfd`. PR27 остаётся черновиком.
Производственный Windows backend не зарегистрирован в CommandConfinement.

## Дельта после a6eb17d: новые изменения

Сохранены AppContainer + Job без виртуализации и сторонних драйверов,
предыдущие исправления PowerShell/RPC и отдельный macOS-коммит `fd4fd47`.
Полные прежние журналы не переписаны.

- `abe8e40`: применено разрешённое точечное снятие ACE свежего SID только
  внутри workspace и прямое восстановление исходных снимков. Перед восстановлением
  проверяются чужие ACE относительно фактически установленного дескриптора;
  при расхождении отказ вместо перезаписи чужих изменений. Очистка temp/cache
  восстанавливает только корневые grants, без рекурсивной перезаписи этих деревьев.
  На Windows Node20 и Node22: независимые исходные дескрипторы **10/10**,
  cleanup=true; Node/cmd/WinPS=0; NUL и hardlink-гейты проходят.
- `595ea79`: добавлен гейт настоящего CrotService с PrivateFileProtection и
  одноразовым SID AppContainer. Владелец аутентифицируется, меняет настройки,
  создаёт секрет и аудит. Из песочницы пять чтений, пять записей и подключение
  к настоящему управляющему каналу получают **EPERM** на обоих Node;
  serviceCode=0, serviceUnchanged=true, ownerStillAuthenticated=true.
  Дескриптор существовавшего скрипта процесса также точно восстановлен.
  Токены и содержимое секретов в доказательства не выводятся.

## CI и доказательства

На обоих исходных коммитах полный локальный npm run check завершён с кодом 0:
Linux x64/Node24, 1748 Core +147 extension, 168 skipped. Это не Windows-проверка.
На последнем коммите девять остальных CI успешны, оба Windows задания неуспешны
из-за прежних restricted-token тестов. AppContainer-тесты проходят на обоих Node.

Полные события, локальные журналы, SHA256 и связь тестировавшихся merge-коммитов
с исходными HEAD: `docs/evidence/windows-l1-workspace-service/`.
Сводка для каждого Node: `595ea79-native-summary.json`; все результаты CI:
`595ea79-checks.json`. Исторические доказательства сохранены отдельно.

## Следующий шаг

Закреплённые handles обычных существовавших узлов workspace сейчас открываются
без FILE_SHARE_DELETE. Это потенциально блокирует обычное переименование и
требует отдельного позитивного теста, а не ослабления ACL-проверки.
Предложенная узкая правка режима совместного открытия и тест записи/переименования
остановлены автоматической проверкой до исполнения; исходники не изменены.
Требуется явное подтверждение: FILE_SHARE_DELETE только для снимков обычных
существовавших узлов workspace, без изменения DACL, защиты предков/корня/внешних
hardlink и без рекурсивных изменений temp/cache; затем новый реальный Windows-прогон
с позитивным переименованием и точным восстановлением всех добавленных снимков.
После закрытия этого риска — безопасная интеграция CommandConfinement и исправление
оставшихся CI-дефектов. WP-23b разблокирован архитектурно, но ещё не реализован;
Linux/macOS/Windows остаются обязательными для v1.
